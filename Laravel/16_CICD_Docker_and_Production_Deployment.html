🌐 Production DevOps Architecture & Zero-Downtime

Live server par git pull karna ya FTP se files drag-drop karna enterprise level par career-ending mistake hoti hai. Samajhiye zero-downtime atomic symlink architecture aur modern cloud topology.

⚠️ The Disaster of In-Place Deployments (Why "git pull" Breaks)

Jab aap live production directory mein git pull origin main && composer install chalate hain, toh deploy hone mein 30 se 90 seconds lagte hain. Is dauran users ko kya face karna padta hai:

Phase / Second What The Server Is Doing What Real Customers Experience (The Nightmare)
0s – 10s git pull updates files on disk ❌ File Desynchronization: New Controller old Model ko call karta hai → Fatal PHP FatalError!
10s – 35s composer install updates vendor/ ❌ Missing Autoloader: Class 'Resend' not found → 500 Internal Server Error for all checkout requests!
35s – 50s npm run build compiles Vite assets ❌ 404 Asset Errors: Users ko CSS/JS files missing milti hain, layout broken white screen ho jata hai!
50s – 70s php artisan migrate alters tables ❌ Column Lock & Deadlocks: Active transactions fail ho jati hain!
After 70s Deployment finishes ⚠️ Customer checkout drop-off, abandoned carts, aur lost revenue!
🏛️ Enterprise Production Architecture Topology (The Symlink Solution)

1. Isolated Release Folders

Har deployment ek fresh timestamped directory (releases/20260909120000/) mein hoti hai. Live site ko touch kiye bina composer, npm build, aur cache compile hote hain.

2. Atomic Symlink Swap

Jab naya release 100% ready ho jaye, Linux ka ln -nfs releases/new current command microsecond (0.001 sec) mein live pointer switch kar deta hai. ZERO downtime!

3. Persistent Shared Directory

Database credentials (.env) aur customer uploads (storage/) ek separate shared/ directory mein rehte hain aur har release mein automatically symlink ho jate hain.

🐳 Production Multi-Stage Dockerfile & Compose

Multi-stage Docker builds se development tools (Node.js, Git, C compilers) final production image se bahar nikal diye jate hain, jisse image size 1.2GB se kam hokar sirf 85MB reh jati hai.

📦 Hardened Production Multi-Stage Dockerfile
dockerfileDockerfile.production
# ==========================================
# STAGE 1: COMPOSER DEPENDENCY BUILDER
# ==========================================
FROM composer:2.7 AS vendor
WORKDIR /app
COPY composer.json composer.lock ./
RUN composer install     --no-dev     --no-interaction     --prefer-dist     --ignore-platform-reqs     --optimize-autoloader     --no-scripts

# ==========================================
# STAGE 2: NODE / VITE ASSET COMPILER
# ==========================================
FROM node:20-alpine AS frontend
WORKDIR /app
COPY package.json package-lock.json vite.config.js ./
RUN npm ci
COPY resources/ resources/
RUN npm run build

# ==========================================
# STAGE 3: MINIMAL PRODUCTION RUNTIME
# ==========================================
FROM php:8.3-fpm-alpine AS runtime

# Install essential production extensions only
RUN apk add --no-cache     mysql-client     libpng-dev     libjpeg-turbo-dev     libwebp-dev     freetype-dev     libzip-dev     zip     unzip     linux-headers     && docker-php-ext-configure gd --with-freetype --with-jpeg --with-webp     && docker-php-ext-install pdo_mysql gd zip opcache bcmath     && pecl install redis     && docker-php-ext-enable redis

# Hardened security: Run as unprivileged www-data user
WORKDIR /var/www/html

# Copy compiled code from prior stages
COPY --chown=www-data:www-data . .
COPY --chown=www-data:www-data --from=vendor /app/vendor /var/www/html/vendor
COPY --chown=www-data:www-data --from=frontend /app/public/build /var/www/html/public/build

# Ensure correct permissions on storage and cache
RUN chown -R www-data:www-data /var/www/html/storage /var/www/html/bootstrap/cache     && chmod -R 775 /var/www/html/storage /var/www/html/bootstrap/cache

USER www-data
EXPOSE 9000
CMD ["php-fpm", "-y", "/usr/local/etc/php-fpm.conf", "-R"]

name: CI/CD Production Deployment

on:
  push:
    branches: [ main ]

jobs:
  # ============================================================
  # STAGE 1: AUTOMATED TEST SUITE & CODE QUALITY GATES
  # ============================================================
  test:
    runs-on: ubuntu-latest
    services:
      mysql:
        image: mysql:8.0
        env:
          MYSQL_ROOT_PASSWORD: root
          MYSQL_DATABASE: testing
        ports:
          - 3306:3306
        options: --health-cmd="mysqladmin ping" --health-interval=10s --health-timeout=5s --health-retries=3

      redis:
        image: redis:7-alpine
        ports:
          - 6379:6379

    steps:
      - name: Checkout Source Code
        uses: actions/checkout@v4

      - name: Setup PHP 8.3 Runtime
        uses: shivammathur/setup-php@v2
        with:
          php-version: '8.3'
          extensions: mbstring, xml, ctype, iconv, mysql, bcmath, redis
          coverage: none

      - name: Install Composer Dependencies
        run: composer install -q --no-ansi --no-interaction --no-scripts --prefer-dist

      - name: Code Style Enforcement (Laravel Pint)
        run: ./vendor/bin/pint --test

      - name: Static Type Analysis (PHPStan / Larastan)
        run: ./vendor/bin/phpstan analyse --memory-limit=2G

      - name: Execute Pest PHP Feature & Unit Tests
        env:
          DB_CONNECTION: mysql
          DB_HOST: 127.0.0.1
          DB_PORT: 3306
          DB_DATABASE: testing
          DB_USERNAME: root
          DB_PASSWORD: root
          CACHE_STORE: redis
          QUEUE_CONNECTION: redis
        run: ./vendor/bin/pest --parallel --compact

  # ============================================================
  # STAGE 2: ZERO-DOWNTIME PRODUCTION DEPLOYMENT RUNNER
  # ============================================================
  deploy:
    needs: test
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'

    steps:
      - name: Execute Remote Zero-Downtime Deployment via SSH
        uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ secrets.SSH_HOST }}
          username: ${{ secrets.SSH_USER }}
          key: ${{ secrets.SSH_PRIVATE_KEY }}
          port: ${{ secrets.SSH_PORT || 22 }}
          script: |
            cd /var/www/shopsphere
            bash deploy.sh

📜 The Production Deployment Script: deploy.sh

Yeh Bash script enterprise standards par build kiya gaya hai — agar kisi bhi step par error aaye, toh set -e execution ko turant abort kar deta hai jisse broken release kabhie bhi live nahi hota:

bash/var/www/shopsphere/deploy.sh
#!/usr/bin/env bash
set -e # Exit immediately if a command exits with a non-zero status

echo "🚀 Starting Zero-Downtime Deployment..."

BASE_DIR="/var/www/shopsphere"
RELEASE_TIMESTAMP=$(date +"%Y%m%d%H%M%S")
RELEASE_DIR="$BASE_DIR/releases/$RELEASE_TIMESTAMP"
SHARED_DIR="$BASE_DIR/shared"

# 1. Clone latest main commit into fresh isolated directory
echo "📦 Cloning latest release into $RELEASE_DIR..."
git clone --depth 1 --branch main git@github.com:shopsphere/shopsphere.git "$RELEASE_DIR"

# 2. Symlink persistent shared .env and storage/ directory
echo "🔗 Linking shared credentials and storage..."
rm -f "$RELEASE_DIR/.env"
ln -s "$SHARED_DIR/.env" "$RELEASE_DIR/.env"

rm -rf "$RELEASE_DIR/storage"
ln -s "$SHARED_DIR/storage" "$RELEASE_DIR/storage"

cd "$RELEASE_DIR"

# 3. Install production PHP packages (No dev tools)
echo "⚡ Installing optimized composer packages..."
composer install --no-dev --prefer-dist --optimize-autoloader --no-interaction -q

# 4. Compile frontend production assets (Vite)
echo "🎨 Compiling frontend assets..."
npm ci --silent
npm run build --silent
rm -rf node_modules

# 5. Run database migrations safely
echo "🗄️ Running database migrations..."
php artisan migrate --force

# 6. Warm all caches in isolated directory
echo "🔥 Compiling configuration and route caches..."
php artisan config:cache
php artisan route:cache
php artisan view:cache
php artisan event:cache

# 7. ATOMIC SYMLINK SWAP (The Zero-Downtime Magic!)
echo "🔄 Activating new release atomically..."
ln -nfs "$RELEASE_DIR" "$BASE_DIR/current"

# 8. Reload PHP-FPM and signal Queue Workers to restart
echo "♻️ Reloading PHP-FPM and Queue Workers..."
sudo systemctl reload php8.3-fpm
php artisan queue:restart

# 9. Purge old releases (Keep last 5 releases only)
echo "🧹 Purging old releases..."
cd "$BASE_DIR/releases"
ls -1t | tail -n +6 | xargs rm -rf 2>/dev/null || true

echo "✅ Deployment successfully completed with 0 seconds downtime!"
🤖 Horizon & Worker Daemon Orchestration

Queue workers long-running PHP processes hote hain jo memory leaks aur fatal exceptions ki wajah se kabhie bhi crash ho sakte hain. Seekhiye Supervisord process supervisor, graceful shutdown, aur single-cron architecture.

⚙️ Supervisord Configuration: Keeping Workers Alive 24/7

Supervisor Linux ka process monitor hai jo background workers ke crash hone par unhe microsecond mein automatically restart kar deta hai:

ini/etc/supervisor/conf.d/shopsphere-worker.conf
[program:shopsphere-worker]
process_name=%(program_name)s_%(process_num)02d
command=php /var/www/shopsphere/current/artisan queue:work redis --queue=high,emails,default --sleep=3 --tries=3 --max-time=3600 --max-jobs=1000
autostart=true
autorestart=true
stopasgroup=true
killasgroup=true
user=www-data
numprocs=4
redirect_stderr=true
stdout_logfile=/var/www/shopsphere/shared/storage/logs/worker.log
stopwaitsecs=3600
💡
Important Supervisor Directives:
• numprocs=4: 4 concurrent background worker processes spawn honge jo parallel jobs process karenge.
• --max-time=3600 & --max-jobs=1000: Har 1 ghante baad ya 1,000 jobs ke baad worker memory clean karne ke liye gracefully exit hoga aur Supervisor use restart kar dega.
• stopwaitsecs=3600: Agar koi heavy video processing ya invoice export chal rahi ho, toh worker ko forcibly terminate karne se pehle poore 1 ghante ka graceful window milega.

⚡ Opcache, Nginx Tuning & Instant Rollback

Production PHP ko zero disk I/O par chalana, Nginx upstream buffers tune karna, automated health checks, aur agar production par naya code fat jaye toh 3 second ke andar instant rollback execute karna.

🔥 Hardened Production Opcache: Zero Disk I/O Execution

PHP normally har request par files ko disk se read karke opcode compile karta hai. Production mein validate_timestamps=0 karke disk reads ko 100% khatam karein:

ini/etc/php/8.3/fpm/conf.d/10-opcache.ini
[opcache]
opcache.enable=1
opcache.enable_cli=0

; 256MB dedicated RAM for pre-compiled PHP opcodes
opcache.memory_consumption=256

; 16MB for interned strings (method names, class strings)
opcache.interned_strings_buffer=16

; Maximum cached PHP script files (Laravel has ~6,000 files with vendor)
opcache.max_accelerated_files=20000

; CRITICAL PRODUCTION SPEEDUP: Never check disk for file updates!
; Opcache compiled memory se execute karega. Zero file I/O overhead!
opcache.validate_timestamps=0

; Fast shutdown sequence
opcache.fast_shutdown=1
⚠️
Warning: validate_timestamps=0 Ka Matlab:
Agar aapne live server par kisi file ko edit kiya, toh PHP-FPM purana code hi execute karta rahega jab tak aap sudo systemctl reload php8.3-fpm na karein! Isiliye hamare deploy.sh script ke aakhir mein PHP-FPM reload command shamil hai.
⏪ The 3-Second Emergency Rollback: rollback.sh

Agar deployment ke 2 minute baad customer payment gateway crash hone lage, toh panic karne ki zaroorat nahi hai. Single command se pichle stable release par wapas chale jayein:

bash/var/www/shopsphere/rollback.sh
#!/usr/bin/env bash
set -e

BASE_DIR="/var/www/shopsphere"
cd "$BASE_DIR/releases"

# 1. Pichla stable release identify karo (2nd most recent release)
PREVIOUS_RELEASE=$(ls -1t | sed -n '2p')

if [ -z "$PREVIOUS_RELEASE" ]; then
    echo "❌ Error: No previous release found to rollback to!"
    exit 1
fi

echo "⏪ Rolling back to release: $PREVIOUS_RELEASE..."

# 2. Atomically swap symlink backwards
ln -nfs "$BASE_DIR/releases/$PREVIOUS_RELEASE" "$BASE_DIR/current"

# 3. Reload PHP-FPM and Queue Workers
sudo systemctl reload php8.3-fpm
php "$BASE_DIR/current/artisan" queue:restart

echo "✅ Rollback completed in under 3 seconds! Live traffic is safe."
