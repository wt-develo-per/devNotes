Authentication (Sanctum vs Passport)

APIs default stateless hoti hain. Iska matlab unhein yaad nahi rehta ki pichli request kisne bheji thi. Har request ke sath identity (Token) bhejna zaruri hai. Let's master the auth architectures.

Architecture Decision

1. Sanctum vs Passport (Kya chunein?)

Laravel mein APIs secure karne ke 2 official packages hain. 4 YOE ke baad aapko pata hona chahiye kab kaunsa use karna hai.

Laravel Sanctum

Use case: Single Page Apps (Vue/React), Mobile Apps (Flutter/React Native), aur simple 3rd party API tokens.

Complexity: Very Low.
Under the hood: Database mein token generate karke hash store karta hai.

Laravel Passport

Use case: Full OAuth2 server (jaise "Login with Google" jahan aap apna "Login with MyApp" banana chahte hain), Machine-to-Machine auth.

Complexity: High.
Under the hood: JWT (JSON Web Tokens), Refresh tokens, Auth codes.

90% Rule

As a senior dev, always default to Sanctum. Jab tak client explicitly OAuth2 architecture maang nahi raha ho, Passport set up karke application ko over-engineer na karein.

Intermediate

2. Issuing API Tokens (Sanctum)

Mobile apps ke liye humein Bearer tokens issue karne hote hain.

AuthController.php (Login Method)
public function login(LoginRequest $request)
{
    $user = User::where('email', $request->email)->first();

    if (! $user || ! Hash::check($request->password, $user->password)) {
        throw ValidationException::withMessages([
            'email' => ['Credentials mismatched.'],
        ]);
    }

    // Delete old tokens if you want only 1 active session per user
    // $user->tokens()->delete(); 

    // Generate new token (The plainTextToken is what you send back)
    $token = $user->createToken('mobile-app')->plainTextToken;

    return $this->successResponse([
        'user' => new UserResource($user),
        'token' => $token
    ], 'Login successful');
}

Frontend ab har request ke header mein bhejega:
Authorization: Bearer 1|laravel_sanctum_token_abc123...

Mastery Implementation

3. Token Abilities (The "Scope" pattern)

Man lijiye aapke pass ek "Read Only" token aur ek "Admin" token generate karne ka feature hai. Sanctum mein ise Abilities kehte hain.

Token generate karte waqt array of abilities pass karein:

$token = $user->createToken('read-only', ['server:read'])->plainTextToken;
$adminToken = $user->createToken('admin', ['server:read', 'server:delete'])->plainTextToken;

Routes ko protect karne ke liye middleware use karein:

routes/api.php
// Request must have a valid token AND that token must have 'server:delete' ability
Route::delete('/server/{id}', [ServerController::class, 'destroy'])
    ->middleware(['auth:sanctum', 'ability:server:delete']);

ℹ️ Abilities vs Roles/Permissions

Abilities token level par hoti hain. Roles/Permissions user level par hote hain. (e.g. Ek SuperAdmin 'read-only' token generate kar sakta hai jo delete nahi kar payega, bhale hi user technically SuperAdmin ho).

Mastery Architecture

4. SPA Cookie Auth (No Tokens Needed!)

Agar aapka frontend (React/Vue) usi domain/subdomain par hosted hai jahan API hai (e.g. api.app.com aur app.com), toh Bearer tokens use karna galat hai. XSS attacks mein JS-stored tokens chori ho sakte hain.

Sanctum ka SPA Authentication automatically stateful cookies (HttpOnly) use karta hai backend aur frontend ke beech. (Like traditional web, but for JSON API).

  • Frontend pehle GET /sanctum/csrf-cookie call karta hai.
  • Laravel ek CSRF token set karta hai as a cookie.
  • Frontend phir POST /login call karta hai (bina Bearer token ke).
  • Axios/Fetch automatically cookies bhejta rehta hai aage ki saari requests mein (kyunki cookies browser level par manage hoti hain).
config/sanctum.php
'stateful' => explode(',', env('SANCTUM_STATEFUL_DOMAINS', sprintf(
    '%s%s',
    'localhost,localhost:3000,127.0.0.1,127.0.0.1:8000,::1',
    env('APP_URL') ? ','.parse_url(env('APP_URL'), PHP_URL_HOST) : ''
))),

SANCTUM_STATEFUL_DOMAINS env var mein apne frontend ka URL set karna hota hai. Uske baad tokens manually handle karne ki zaroorat hi nahi hoti!
