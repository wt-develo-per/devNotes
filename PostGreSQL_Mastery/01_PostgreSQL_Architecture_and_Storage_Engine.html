⚙️ Core Architecture • Part 1 • Process Model & Memory Layout

PostgreSQL Multi-Process Architecture & Memory Hierarchy

MySQL ke thread-based model ke opposite, PostgreSQL ek process-based fork architecture use karta hai. Ek 4 YOE Senior Engineer ko pata hona chahiye ki har connection server memory ko kaise affect karta hai aur core background daemons ka kya role hai.

🐬 MySQL Developer Mental Bridge: Process vs Thread Architecture

• MySQL (Thread-per-connection): Single mysqld process chalta hai. Har client connection ke liye ek lightweight OS thread banta hai (~256KB RAM). Connection establishment bohot fast hoti hai.
• PostgreSQL (Process-per-connection): Master process (postmaster) har connection ke liye pura OS process fork() karta hai (~5MB - 10MB RAM). Crash isolation perfect hoti hai (ek client crash se baki server safe rehta hai), lekin high connections par CPU context-switching badh jaata hai.
• Production Impact: MySQL mein aap max_connections = 500 aasaani se rakh sakte the. PostgreSQL mein 500 connections par server choke ho jayega; isiliye PostgreSQL mein PgBouncer connection pooling mandatory hoti hai!

PostgreSQL High-Level Architectural Flow

1. Client & Postmaster

• Client connects to port 5432.
• Postmaster daemon connection authenticate karta hai.
• Postmaster fork() call karke ek dedicated Backend Process create karta hai.
• Backend process client lifecycle tak zinda rehta hai.

2. Shared Memory Area

• Shared Buffers: 8KB table/index pages cache (~25% of system RAM).
• WAL Buffers: Uncommitted transaction logs (~16MB).
• Lock Space: Table, row & advisory locks hash table.
• pg_xact (CLOG): Transaction commit status bits (2 bits per txid).

3. Background Helper Daemons

• Background Writer (bgwriter): Flushes dirty shared buffers smoothly.
• Checkpointer: Periodic full flush of dirty buffers to disk.
• WAL Writer: Writes WAL buffers to disk.
• Autovacuum Daemon: Dead tuples cleanup & statistics.

🧠 Memory Allocation: Shared vs Local Process Memory

MySQL ke innodb_buffer_pool_size ke sath compare karein:

🏢
shared_buffers vs innodb_buffer_pool
MySQL mein innodb_buffer_pool_size server RAM ka 70% - 80% set kiya jata hai. Lekin PostgreSQL mein shared_buffers sirf 25% rakha jata hai! Kyu? Kyunki PostgreSQL baki 50-60% RAM ko Linux OS kernel ke Page Cache ke liye chhod deta hai (double buffering synergy).
⚡
work_mem (Allocated Per Operation!)
MySQL ke sort_buffer_size jaisa, lekin PostgreSQL mein work_mem per-connection ya per-query nahi hota, balki per-sort / per-hash operation allocate hota hai! Agar ek complex query mein 4 ORDER BY aur 2 Hash Joins hain, toh wo query 6 × work_mem RAM le sakti hai!
🛠️
maintenance_work_mem
Heavy maintenance jobs jaise VACUUM, CREATE INDEX, aur ALTER TABLE ADD FOREIGN KEY ke liye use hota hai. Default 64MB bohot slow hota hai; production servers par ise 1GB - 2GB set karein.
SQL • Inspecting Active Server Processes & Memory Settings 
-- 1. Check current backend process ID and memory parameters
SELECT pg_backend_pid() AS my_process_id;

SHOW shared_buffers;           -- E.g. '16GB' or '128MB' (Compare with MySQL innodb_buffer_pool_size)
SHOW work_mem;                 -- E.g. '4MB' (Compare with MySQL sort_buffer_size)
SHOW maintenance_work_mem;     -- E.g. '1GB'

-- 2. Inspect all active backend processes (Equivalent to MySQL: SHOW FULL PROCESSLIST;)
SELECT 
    pid, 
    usename, 
    application_name, 
    client_addr, 
    state, 
    wait_event_type, 
    wait_event, 
    NOW() - query_start AS query_duration,
    query 
FROM pg_stat_activity 
WHERE state != 'idle' 
ORDER BY query_start ASC;

-- 3. Check background writer and checkpointer activity metrics
SELECT 
    checkpoints_timed, 
    checkpoints_req, 
    checkpoint_write_time, 
    checkpoint_sync_time, 
    buffers_checkpoint, 
    buffers_clean, 
    maxwritten_clean, 
    buffers_backend 
FROM pg_stat_bgwriter;

🎯 4 YOE Architectural Rule:

Agar checkpoints_req (forced checkpoints due to WAL size) checkpoints_timed (scheduled checkpoints) se zyada hai, iska matlab aapka WAL generation bohot fast hai aur checkpoint interval chhota pad raha hai! You must increase max_wal_size to reduce disk I/O thrashing.

📦 Storage Architecture • Part 2 • 8KB Block Anatomy & On-Disk Layout

Storage Engine Internals: The Anatomy of an 8KB Page

PostgreSQL table rows ko flat files mein dump nahi karta. Har table disk par 8192-byte (8KB) Pages (Blocks) ke structured array mein store hoti hai. Samajhiye byte-level page layout aur ctid pointer arithmetic.

🐬 MySQL Developer Mental Bridge: Clustered Tables vs Heap Tables

• MySQL InnoDB (Clustered Index / IOT): MySQL mein table ka data Primary Key ke B-Tree ke leaf nodes mein physically sorted store hota hai. Secondary indexes row data ko directly point nahi karte; wo Primary Key value store karte hain (Double-lookup penalty)!
• PostgreSQL (Heap Storage Model): PostgreSQL mein tables un-ordered Heaps hoti hain. Row kisi bhi 8KB block mein jahan jagah mile insert ho jati hai. Sabhi indexes (including Primary Key!) row ke physical disk address ctid = (block_number, tuple_offset) ko directly point karte hain!
• Page Size: MySQL InnoDB 16KB pages use karta hai, jabki PostgreSQL 8KB pages use karta hai. Chhota 8KB page OLTP random queries ke liye memory efficient hota hai.

📁
Physical File Segmentation (1GB Limit)
Har table filesystem par $PGDATA/base/<db_oid>/<filenode> file mein hoti hai. PostgreSQL kisi bhi single file ko 1GB se bada nahi banata. Agar table 5GB hai, toh disk par 16384, 16384.1, 16384.2 segments ban jaate hain.
📐
The Fixed 8192-Byte Page Standard
Linux OS page standard 4KB hota hai, jabki PostgreSQL ka default BLCKSZ = 8192 bytes hota hai. Har Disk Read ya Write operation minimum 1 pura 8KB block fetch karta hai (kabhi single row akeli nahi aati).
🍞
TOAST (Oversized Attributes)
Kyunki ek row 8KB se badi nahi ho sakti, agar koi column (TEXT, JSONB, BYTEA) ~2KB (1/4th block) se bada hota hai, toh PostgreSQL use transparently compress karke alag pg_toast table mein out-of-line store karta hai.
Byte-Level Anatomy of an 8KB PostgreSQL Block (Page)
+-------------------------------------------------------------------------------+
| 1. PAGE HEADER (24 Bytes) |
| pd_lsn (8B) | pd_checksum (2B) | pd_flags (2B) | pd_lower (2B) | pd_upper (2B) |
+-------------------------------------------------------------------------------+
| 2. LINE POINTERS ARRAY (ItemIds: 4 Bytes each) ▼ Grows Downwards |
| ItemId[1] (offset, flags, len) | ItemId[2] | ItemId[3] ... |
+ - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - +
| ▼ pd_lower points here |
| |
| FREE SPACE HOLE |
| (Shrinks as rows are inserted) |
| |
| ▲ pd_upper points here |
+ - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - +
| 3. TUPLE DATA (Rows) ▲ Grows Upwards from Byte 8192 |
| Tuple 3 (Data) | Tuple 2 (Data) | Tuple 1 (Data) |
+-------------------------------------------------------------------------------+
| 4. SPECIAL SPACE (Index pages only, e.g. B-tree left/right sibling links) |
+-------------------------------------------------------------------------------+

🎯 Understanding ctid: The Physical Tuple Pointer

PostgreSQL mein har row ka ek hidden system attribute hota hai jise ctid kehte hain. Iska format hota hai (block_number, tuple_index):

SQL • Inspecting Physical Tuple Addresses (ctid) 
-- Create sample table and inspect physical ctid
CREATE TABLE users_demo (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(100)
);

INSERT INTO users_demo (name, email) VALUES 
('Rahul Sharma', 'rahul@example.com'),
('Priya Patel', 'priya@example.com');

-- Query the hidden ctid column
SELECT ctid, id, name, email FROM users_demo;

-- OUTPUT:
--   ctid   | id |     name     |       email
-- ---------+----+--------------+-------------------
--  (0,1)   |  1 | Rahul Sharma | rahul@example.com
--  (0,2)   |  2 | Priya Patel  | priya@example.com
--
-- Interpretation: (0, 1) means: Page/Block 0, ItemId Line Pointer #1!

🔬 Deep Inspection with pageinspect Extension

Senior DBAs disk par 8KB block ke bytes ko decode karne ke liye PostgreSQL ka native pageinspect extension use karte hain:

SQL • Using pageinspect to read raw disk blocks 
-- 1. Enable page inspection extension
CREATE EXTENSION IF NOT EXISTS pageinspect;

-- 2. Inspect raw page header of Block 0
SELECT 
    lsn, 
    checksum, 
    flags, 
    lower AS free_space_start_offset, 
    upper AS free_space_end_offset, 
    special, 
    pagesize 
FROM page_header(get_raw_page('users_demo', 0));

-- 3. Inspect individual Line Pointers (ItemIds) and Tuple Headers inside Block 0
SELECT 
    lp, 
    lp_off AS byte_offset, 
    lp_flags, 
    lp_len AS tuple_byte_length, 
    t_xmin, 
    t_xmax, 
    t_ctid 
FROM heap_page_items(get_raw_page('users_demo', 0));
🔄 Concurrency Internals • Part 3 • MVCC, Tuple Headers & Visibility

Multi-Version Concurrency Control (MVCC) Under the Hood

PostgreSQL ka golden rule: "Readers never block Writers, Writers never block Readers." Yeh guarantee MVCC ke hidden tuple headers (xmin / xmax) ke through achieve hoti hai.

🐬 MySQL Developer Mental Bridge: Undo Log vs Heap Tuple Versioning

• MySQL (Undo Log Model): Jab aap MySQL mein UPDATE users SET name='Pankaj' karte hain, MySQL usi 16KB block mein row ko in-place modify karta hai, aur purana data alag Undo Log (Rollback Segment) mein bhej deta hai. Purane readers Undo log padhte hain.
• PostgreSQL (No Undo Log!): PostgreSQL mein Undo Log hota hi nahi hai! Jab aap UPDATE karte hain, purana row table ke andar hi rehta hai (sirf xmax mark hota hai), aur ek brand new row table heap mein insert hoti hai (with new xmin).
• The Consequence: MySQL mein updates se Undo tablespace grow hota hai. PostgreSQL mein updates se main table bloat hoti hai! Yahi reason hai ki PostgreSQL ko VACUUM ki zaroorat padti hai, jabki MySQL ko nahi!

⚡
The Shocking Truth About UPDATEs in PostgreSQL

Traditional relational databases (jaise Oracle ya MySQL InnoDB) row ko in-place update karte hain aur old values ko Undo Log mein bhejte hain. PostgreSQL mein koi in-place UPDATE nahi hota!
PostgreSQL mein UPDATE statement physically ek INSERT (naya tuple) + ek DELETE (purane tuple par xmax mark karna) hota hai! Agar aap ek row ko 50 baar update karte hain, toh disk par 50 alag physical tuples ban jaate hain!

🧬 Anatomy of the 23-Byte Heap Tuple Header

Har row ke aage ek 23-byte ka compact header attach hota hai jisme transaction metadata hoti hai:

🟢
t_xmin (Creating Transaction ID)
Jis transaction ne is row ko INSERT kiya tha, uska 32-bit Transaction ID (txid). Yeh batata hai ki row kab create hui.
🔴
t_xmax (Expiring Transaction ID)
Agar row active hai toh t_xmax = 0. Agar row ko kisi transaction ne UPDATE ya DELETE kiya hai, toh uska txid yahan store hota hai.
📍
t_ctid (Version Forwarding Pointer)
Agar row update ho chuki hai, toh purane tuple ka t_ctid naye updated tuple ke physical block address ko point karta hai (version chain).
Visual Step-by-Step Row Mutation in MVCC

Step 1: INSERT (txid: 200)

Row 1: [Rahul | rahul@mail.com]
xmin: 200
xmax: 0 (Alive)
ctid: (0, 1)
Visible to any transaction starting after 200 commits.

Step 2: UPDATE (txid: 250)

Old Tuple: [Rahul | rahul@mail.com]
xmin: 200 | xmax: 250 (Dead)
ctid points to ▶ (0, 2)

New Tuple: [Rahul S. | rahul@mail.com]
xmin: 250 | xmax: 0 (Alive)

Step 3: DELETE (txid: 300)

Active Tuple: [Rahul S.]
xmin: 250
xmax: 300 (Marked Dead)

Row physically exists on disk! Not visible to txid > 300.

📸 How Snapshots Determine Visibility

Jab koi query run hoti hai, PostgreSQL memory mein ek Snapshot create karta hai jiska internal format hota hai: xmin:xmax:xip_list:

SQL • Inspecting Transaction IDs and Snapshots 
-- 1. Check current transaction ID
SELECT pg_current_xact_id();

-- 2. Inspect active snapshot of current session
SELECT pg_current_snapshot();
-- Example Output: '1020:1025:1021,1023'
-- Explanation:
-- 1020 (xmin): All txids < 1020 are COMMITTED and visible.
-- 1025 (xmax): All txids >= 1025 started AFTER this snapshot and are INVISIBLE.
-- 1021, 1023 (xip): In-progress active transactions (invisible).

-- 3. Live Demo: Inspect xmin/xmax on a real table
CREATE TABLE balance (
    account_id INT PRIMARY KEY,
    amount NUMERIC(10,2)
);

INSERT INTO balance VALUES (1, 5000.00);

-- Query the hidden xmin & xmax columns directly
SELECT xmin, xmax, ctid, account_id, amount FROM balance;

-- Update balance and observe new tuple creation
UPDATE balance SET amount = 7500.00 WHERE account_id = 1;

-- Notice that xmin changed and ctid jumped from (0,1) to (0,2)!
SELECT xmin, xmax, ctid, account_id, amount FROM balance;
🧹 Table Maintenance • Part 4 • Bloat, VACUUM & Autovacuum Tuning

Table Bloat, VACUUM Mechanics & Production Autovacuum Tuning

MVCC ka dark side: Dead tuples table aur indexes ko bloated kar dete hain, jisse disk space waste hoti hai aur sequential scans 10x slow ho jaate hain. Samajhiye VACUUM, HOT updates aur autovacuum ke core configuration levers.

🐬 MySQL Developer Mental Bridge: Why Doesn't MySQL Need VACUUM?

• MySQL (Automatic Purge Threads): MySQL InnoDB mein background innodb_purge_threads hote hain. Jab sabhi active transactions commit ho jaati hain, toh purge threads Undo Log ke purane versions ko background mein bina table ko disturb kiye clean kar dete hain. MySQL tables mein dead tuples ka heap bloat nahi banta.
• PostgreSQL (Autovacuum Mandatory): Kyunki PostgreSQL mein dead rows main table file ke andar hi rehti hain, PostgreSQL ko Autovacuum Daemon chalana padta hai jo har 8KB page ko scan karke dead line pointers ko mark karta hai aur Free Space Map (_fsm) update karta hai.
• Warning: Agar MySQL developer PostgreSQL par switch karke autovacuum ko ignore karega, toh 6 mahine mein tables 5x bloated ho jayengi aur server out of disk ho jayega!

🗺️
Free Space Map (_fsm)
Har table ke sath ek _fsm file banti hai jo har 8KB block mein available unallocated bytes ko track karti hai. Iske bina PostgreSQL ko har naye insert ke liye disk file grow karni padti.
👁️
Visibility Map (_vm) & Index-Only Scans
Har 8KB page ke liye 2 bits track hote hain: "Kya is page ke sabhi tuples sabhi transactions ke liye visible hain?" Agar yes, toh index scan direct result return kar sakta hai bina main heap table ko touch kiye (Index-Only Scan)!
🚀
HOT (Heap-Only Tuples) Optimization
Agar aapka UPDATE kisi index column ko touch nahi karta aur usi 8KB page mein space hai, toh PostgreSQL naye index entries create nahi karta! Naya tuple usi page ke purane tuple se directly chain ho jata hai.

⚔️ Standard VACUUM vs VACUUM FULL vs pg_repack

Operation Lock Taken Reclaims OS Disk Space? Production Safe? When to Use
VACUUM (Standard) ShareUpdateExclusiveLock (Allows reads & writes) ❌ No (Keeps space in internal FSM) ✅ 100% Safe anytime Routine maintenance, dead tuple cleanup, updates VM.
VACUUM FULL AccessExclusiveLock (Blocks ALL reads & writes) ✅ Yes (Shrinks file size on disk) 🚨 DANGEROUS (Can take hours) Maintenance windows only when table is 80%+ bloated.
pg_repack (Extension) Lightweight locks (Allows live reads & writes) ✅ Yes (Shrinks file on disk online) ✅ Enterprise Standard Zero-downtime online table bloat reclamation.

⚙️ Enterprise Autovacuum Tuning Formula

PostgreSQL ke default settings 2005 ke hardware ke liye hain (scale_factor = 0.20). Iska matlab 100 Million rows ki table par autovacuum tab tak trigger nahi hoga jab tak 20 Million rows update ya delete na ho jayein! Isko turant tune karein:

INI • /etc/postgresql/postgresql.conf Autovacuum Settings 
# --- PRODUCTION AUTOVACUUM TUNING ---

# 1. Trigger threshold: 5% modifications instead of default 20%
autovacuum_vacuum_scale_factor = 0.05
autovacuum_vacuum_threshold = 1000

# 2. Parallel Workers: Increase from 3 to 5-8 on modern multicore servers
autovacuum_max_workers = 6

# 3. I/O Cost Budget: Defaults (200 cost, 2ms sleep) choke vacuum on SSDs!
# Increase cost limit so vacuum runs 10x faster without artificially pausing
autovacuum_vacuum_cost_limit = 2000
autovacuum_vacuum_cost_delay = 2ms

# 4. Dedicated maintenance memory for vacuum worker allocations
maintenance_work_mem = 1024MB
SQL • Monitoring Dead Tuples & Bloat in Real-Time 
-- Check live vs dead tuples and last vacuum timestamps
SELECT 
    schemaname, 
    relname AS table_name, 
    n_live_tup AS live_rows, 
    n_dead_tup AS dead_rows, 
    ROUND(n_dead_tup::NUMERIC / NULLIF(n_live_tup + n_dead_tup, 0) * 100, 2) AS dead_tuple_percent,
    last_vacuum, 
    last_autovacuum, 
    last_analyze 
FROM pg_stat_user_tables 
ORDER BY n_dead_tup DESC 
LIMIT 10;

-- Custom per-table autovacuum tuning for ultra-high write audit logs
ALTER TABLE audit_logs SET (
    autovacuum_vacuum_scale_factor = 0.01,
    autovacuum_vacuum_threshold = 500
);
📝 ACID Durability • Part 5 • WAL, Checkpoints & Crash Recovery

Write-Ahead Logging (WAL), Checkpoint Mechanics & Crash Recovery

Har COMMIT par agar PostgreSQL pura 8KB data page disk par likhta, toh disk I/O chauthai second mein choke ho jata. Samajhiye WAL ka sequential append model, LSN arithmetic aur crash recovery pipeline.

🐬 MySQL Developer Mental Bridge: Dual Logs (Redo + Binlog) vs Unified WAL

• MySQL (Dual Logs): MySQL mein do alag logging systems hote hain: Redo Log (ib_logfile) jo InnoDB crash recovery handle karta hai, aur Binlog (mysql-bin) jo replication aur point-in-time recovery handle karta hai. Iske liye MySQL ko internally Two-Phase Commit (XA 2PC) chalana padta hai.
• PostgreSQL (Unified WAL): PostgreSQL mein koi Binlog alag se nahi hota! Ek single, elegant Write-Ahead Log (WAL) crash recovery bhi karta hai, streaming replication bhi karta hai, aur point-in-time backups bhi karta hai.
• LSN vs GTID: MySQL replication mein GTID (Global Transaction Identifier) use hota hai, jabki PostgreSQL mein pure byte-level LSN (Log Sequence Number) offset use hota hai.

💡
The Core Principle of Write-Ahead Logging

"No data page can be written to disk before the WAL record describing that change has been flushed to durable storage!"
PostgreSQL shared buffers mein dirty pages ko memory mein rakhta hai, aur sirf chhota sequential binary log (WAL) disk par sync (fsync) karta hai. Isse random disk writes avoid hote hain aur 100x high transaction throughput milta hai.

🔢
LSN (Log Sequence Number)
WAL stream mein har byte ka ek unique 64-bit integer address hota hai (e.g. 0/16B38E0). Har 8KB data page ke header mein pd_lsn hota hai jo batata hai ki is page par aakhri modification kis LSN par hui thi.
🛑
Checkpoint: The I/O Baseline
Checkpoint ek point-in-time barrier hota hai. Checkpointer sabhi memory ke dirty shared buffers ko disk par flush karta hai aur control file (pg_control) ko update karta hai. Iske pehle ke old WAL segments recycle ho jaate hain.
🛡️
Torn Page & full_page_writes
Agar OS power failure ke waqt 8KB block ka sirf 4KB likh paaye (Torn Page corruption), toh standard recovery fail ho jayegi. Isiliye checkpoint ke baad kisi page ke first modification par PostgreSQL pura 8KB block WAL mein likhta hai (full_page_writes = on).

🔄 Crash Recovery Walkthrough: The REDO Pipeline

How PostgreSQL Recovers Uncommitted State After Power Failure

1. Read pg_control

Crash ke baad jab server boot hota hai, toh sabse pehle $PGDATA/global/pg_control read karta hai aur last successful Checkpoint REDO LSN locate karta hai.

2. Replay REDO Log

Checkpoint LSN se aage jitne bhi WAL records hain, unhe sequential order mein replay kiya jata hai. Agar page.pd_lsn >= record.lsn hai, toh replay skip ho jata hai (already on disk).

3. Rollback & Open

Uncommitted transactions ko abort mark kiya jata hai in pg_xact (CLOG). Database completely consistent state mein open ho jata hai with ZERO data loss!

⚙️ Production Checkpoint Tuning Levers

Frequent checkpoints disk I/O spikes create karte hain. Production servers ke liye smooth checkpointing enable karein:

INI • postgresql.conf Checkpoint Parameters 
# Checkpoint time interval: 15 to 30 minutes in production
checkpoint_timeout = 15min

# Maximum WAL generated before forcing an unexpected checkpoint
# Increase from 1GB to 16GB-32GB on modern storage
max_wal_size = 16GB
min_wal_size = 2GB

# Smooth Checkpointing: Spread the writes over 90% of the timeout
# This prevents sudden disk write IOPS spikes!
checkpoint_completion_target = 0.9

# Keep full page writes enabled for crash safety
full_page_writes = on

# WAL Buffer size
wal_buffers = 16MB
SQL • Inspecting WAL Activity & Calculating Write Volume 
-- 1. Check current WAL insert position
SELECT pg_current_wal_lsn();

-- 2. Measure bytes written between two time intervals
WITH before_bench AS (
    SELECT pg_current_wal_lsn() AS lsn
),
after_bench AS (
    -- Run heavy queries here...
    SELECT pg_current_wal_lsn() AS lsn
)
SELECT pg_size_pretty(pg_wal_lsn_diff(after_bench.lsn, before_bench.lsn)) AS wal_bytes_generated
FROM before_bench, after_bench;

-- 3. Check WAL file location and archive status
SELECT pg_walfile_name(pg_current_wal_lsn());

🔬 Critical System Catalog Diagnostic Queries

SQL • Top 10 Largest Tables with Table vs Index Sizes 
SELECT 
    schemaname,
    relname AS table_name,
    pg_size_pretty(pg_table_size(relid)) AS data_size,
    pg_size_pretty(pg_indexes_size(relid)) AS index_size,
    pg_size_pretty(pg_total_relation_size(relid)) AS total_size
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC
LIMIT 10;
SQL • Shared Buffers Cache Hit Ratio (Should be > 99%) 
SELECT 
    datname AS database_name,
    blks_read,
    blks_hit,
    ROUND(blks_hit::NUMERIC / NULLIF(blks_hit + blks_read, 0) * 100, 2) AS cache_hit_ratio_percent
FROM pg_stat_database
WHERE datname = current_database();
-- If cache_hit_ratio is < 98%, your shared_buffers is too small or queries lack indexes!
SQL • Finding Unused Indexes Wasting Write IOPS 
-- Spot indexes that have never been used by the query planner
SELECT 
    schemaname,
    relname AS table_name,
    indexrelname AS index_name,
    idx_scan AS number_of_scans,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
JOIN pg_index USING (indexrelid)
WHERE indisunique IS FALSE
  AND idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
SQL • Terminating Long-Running or Blocking Queries 
-- Soft Cancel: Gracefully requests query to abort (SIGINT)
SELECT pg_cancel_backend(12345);

The TXID Wraparound Catastrophe (Every Senior Engineer Must Know)

PostgreSQL mein Transaction IDs 32-bit unsigned integers hote hain (Max ~4.29 Billion).
PostgreSQL circular modular arithmetic use karta hai: kisi bhi waqt 2.14 Billion txids "past" mein hote hain, aur 2.14 Billion txids "future" mein.
The Catastrophe: Agar aapki database 2.14 Billion transactions run kar leti hai aur old rows freeze nahi hoti hain, toh past transactions wrap around hokar "FUTURE" ban jaayengi—jisse pura table data achanak gayab (invisible) ho jayega!
PostgreSQL Protection: Agar age(datfrozenxid) 200 Million pahuchti hai, toh aggressive freeze autovacuum trigger hota hai. Agar age 2.13 Billion ho jaaye aur problem solve na ho, toh PostgreSQL data loss prevent karne ke liye completely shut down ho jata hai aur sirf single-user mode mein restart hota hai!

🔍 Monitoring Database Transaction ID Age

SQL • Checking Database TXID Wraparound Danger 
-- Check TXID age for all databases (Danger zone if > 1,000,000,000)
SELECT 
    datname,
    age(datfrozenxid) AS oldest_unfrozen_xid_age,
    2^31 - 1000000 - age(datfrozenxid) AS transactions_until_emergency_shutdown
FROM pg_database
ORDER BY oldest_unfrozen_xid_age DESC;

⚔️ Architectural Comparison: PostgreSQL vs MySQL

Feature PostgreSQL MySQL (InnoDB) Senior Engineering Trade-off
Connection Model Process-per-connection (fork) Thread-per-connection PG has strong process memory isolation, but requires PgBouncer pooling.
UPDATE Internals INSERT new tuple + mark old dead In-place update with Undo Log PG requires regular VACUUM to prevent bloat; MySQL avoids heap bloat.
Crash Isolation Single backend segfault isolates cleanly Thread crash can kill mysqld daemon PostgreSQL is significantly more resilient to buggy C extensions.
Default Block Size 8192 Bytes (8 KB) 16384 Bytes (16 KB) PG handles small random OLTP reads efficiently with less I/O amplification.
