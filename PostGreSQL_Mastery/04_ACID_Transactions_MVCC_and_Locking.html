🛡️ Core Concepts • Part 1 • Foundations

Understanding ACID Transactions

Ek production database ko reliable banata hai uska ACID compliance. Ye 4 principles ensure karte hain ki server crash hone par bhi data corrupt na ho.

🅰️
Atomicity (All or Nothing)
Agar ek transaction me 5 queries hain, toh ya toh paancho pass hongi, ya ek bhi nahi. Agar 4th query fail hui, toh pehli 3 automatic ROLLBACK ho jayengi.
🅲
Consistency
Transaction ke baad database hamesha ek valid state me rahega. Saare constraints (Unique, Foreign Keys, Checks) verify honge.
🅸
Isolation
Do log ek sath same row modify kar rahe hain, toh dono ki queries ek dusre se "isolated" (alag) rahengi jab tak commit na ho. (Isi ke liye MVCC use hota hai!)
🅳
Durability
Ek baar COMMIT ho gaya, to agar agle second server ki light chali jaye ya crash ho jaye, data disk pe safe rahega (via WAL - Write-Ahead Logging).
SQL • Basic Transaction Syntax 
-- Start a transaction
BEGIN; 
-- (You can also use 'START TRANSACTION;')

-- Decrease balance from Account A
UPDATE accounts SET balance = balance - 100 WHERE id = 1;

-- Increase balance in Account B
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- If everything looks good, save changes permanently
COMMIT;

-- Or, if something went wrong in your application logic, undo everything
-- ROLLBACK;
🕰️ Concurrency • Part 2 • Multi-Versioning

MVCC (Multi-Version Concurrency Control)

"Readers don't block writers, and writers don't block readers." PostgreSQL ye magic kaise karta hai bina database ko lock kiye?

🤔 The Problem without MVCC

Imagine User A is running a big report taking 2 minutes. Suddenly User B updates a row that the report is reading. Purane databases me User B ko wait karna padta jab tak report complete na ho (Locking).

The xmin & xmax System

PostgreSQL ek row ko in-place overwrite (update) nahi karta. Jab aap UPDATE karte hain, PG ek nayi row banata hai. Har row ke paas hidden tracking IDs hoti hain:

Hidden Column What it does Real-world meaning
xmin Transaction ID that inserted/created the row "Kiske time pe ye row paida hui thi?"
xmax Transaction ID that deleted/updated the row "Kiske time pe ye row mark as dead/deleted hui?"
SQL • Uncovering the hidden MVCC columns 
-- Check the hidden transaction IDs for your rows
SELECT xmin, xmax, id, name FROM users;

/* Output:
  xmin  | xmax | id | name
--------+------+----+-------
 1045   | 0    | 1  | Alice    <-- Alive! (xmax is 0)
*/

-- Transaction 1050 runs: UPDATE users SET name = 'Alicia' WHERE id = 1;

/* Under the hood, PG marks the old row as dead (xmax=1050), 
   and creates a brand new row (xmin=1050, xmax=0) */
   
/* Output to disk:
  xmin  | xmax | id | name
--------+------+----+-------
 1045   | 1050 | 1  | Alice    <-- Dead row (marked for Autovacuum)
 1050   | 0    | 1  | Alicia   <-- New live row
*/
🐬 Architectural Shift • Part 3 • The Mental Bridge

MySQL InnoDB vs PostgreSQL MVCC

Dono MVCC use karte hain, par dono ka design absolutely opposite hai! As an experienced MySQL dev, ye difference aapko zaroor pata hona chahiye.

🐬 MySQL InnoDB (Undo Logs)

• In-place Update: Jab aap MySQL me UPDATE chalate ho, wo physical row ko directly modify kar deta hai.

• Undo Logs: Purana data "Undo Logs" (Rollback segments) me chala jata hai.

• Pros: Tables me bloat/kachra (dead rows) nahi banta. No need for heavy Vacuum.

• Cons: Undo logs maintain karna expensive hai. Long running transactions MySQL system space ko fill kar dete hain.

🐘 PostgreSQL (Tuple-based MVCC)

• Append-Only Update: UPDATE is practically an INSERT + DELETE. Purani row wahi rehti hai bas xmax mark ho jati hai.

• No Undo Logs: Past versions table ke andar hi exist karte hain.

• Pros: Rollback is almost instant (just ignore the new row). Super fast writing.

• Cons: Table Bloat! Dead rows table size badhati rehti hain. Yahi reason hai ki PostgreSQL me Autovacuum zaroori hai (to clean up xmax rows).

🧱 Isolation • Part 4 • Read Phenomena

Transaction Isolation Levels

Jab 2 users ek sath update karein to kya database unhe prevent karega? Ye depend karta hai aapke Isolation level par.

Isolation Level Dirty Read Non-repeatable Read Phantom Read When to use?
Read Uncommitted Yes (But PG blocks it) Yes Yes PG treats this same as Read Committed.
Read Committed (PG Default) No Yes Yes 99% of web apps. Fast, minimal locking.
Repeatable Read (MySQL Default) No No No (in PG) Financial reports, calculating totals over time.
Serializable No No No Strict banking, double-booking prevention. Slowest!

🐬 MySQL Developer Mental Bridge: Default Isolation

Notice kiya? MySQL ka default isolation REPEATABLE READ hota hai, jabki PostgreSQL aur baaki sabhi (SQL Server, Oracle) ka default READ COMMITTED hota hai!

Iska matlab agar MySQL me aapne transaction start kiya, toh aapko pure transaction life me data waisa hi dikhega jaisa start me tha (Snapshot). PostgreSQL me default behavior me agar beech me kisi ne row update kardi aur commit kardi, to aapko new value dikhegi (Non-repeatable read).

🔒 Locking • Part 5 • Resolving Conflicts

Locks & Deadlocks

Isolation rules ko enforce karne ke liye database Locks lagata hai. Table-level aur Row-level locks kaise kaam karte hain, lets see.

🛑
Row-Level Locks
Jab aap UPDATE users karte ho, toh sirf target row lock hoti hai. Dusre users dusri rows ko update kar sakte hain. Use SELECT ... FOR UPDATE to explicitly lock rows for processing (like consuming queue jobs).
💥
Deadlocks
TxA locks Row 1 and wants Row 2. TxB locks Row 2 and wants Row 1. They wait forever. PG detects this and auto-kills one transaction with a deadlock detected error. Handle this in your app code via retries!
SQL • Preventing Race Conditions (Pessimistic Locking) 
BEGIN;

-- Lock the specific user row so NO ONE ELSE can modify it
-- or even do a 'SELECT FOR UPDATE' on it until we COMMIT
SELECT balance FROM wallets WHERE user_id = 123 FOR UPDATE;

-- Application checks if balance > 50
-- If true:
UPDATE wallets SET balance = balance - 50 WHERE user_id = 123;

-- Release the lock
COMMIT;

⚠️ Avoid DDL in Peak Hours

Operations like ALTER TABLE or creating an index normally take an Access Exclusive Lock on the entire table. Ye kisi bhi SELECT ko bhi block kar deta hai!
Pro Tip: Hamesha CREATE INDEX CONCURRENTLY use karein production me, ye table ko lock nahi karta!
