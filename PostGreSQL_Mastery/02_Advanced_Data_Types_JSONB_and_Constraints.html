🔢 Data Fundamentals • Part 1 • Primitives & Modern Primary Keys

Numbers, Strings & Primary Keys: The Myths vs Reality

Beginner se Senior level tak: Kyu PostgreSQL mein VARCHAR(255) likhna ek purani aadat hai, floating-point numbers paiso ke hisab mein kyu fail hote hain, aur UUIDv7 ne database primary keys ko kaise revolutionize kiya.

🐬 MySQL Developer Mental Bridge: Primary Keys & VARCHAR Habits

• AUTO_INCREMENT vs IDENTITY: MySQL mein hum id INT AUTO_INCREMENT PRIMARY KEY likhte the. PostgreSQL mein SERIAL legacy tha, aur modern PG 10+ standard BIGINT GENERATED ALWAYS AS IDENTITY hai.
• VARCHAR(255) Habit: MySQL mein internal memory buffer allocations ke liye developers har column par VARCHAR(255) lagate the. PostgreSQL mein TEXT aur VARCHAR(n) exact same varlena C-structure use karte hain—isiliye PostgreSQL mein VARCHAR(255) likhne ka koi performance benefit nahi hota! Bejhijhak TEXT use karein.
• UUIDv7 over AUTO_INCREMENT: Distributed microservices aur SaaS apps mein sequential IDs leak hone (e.g. api/invoices/101) se bachne ke liye UUIDv7 modern standard ban chuka hai.

💡
Myth: "VARCHAR(255) is Faster than TEXT"
MySQL habit ki wajah se log VARCHAR(255) likhte hain. Lekin PostgreSQL mein TEXT aur VARCHAR under-the-hood bilkul identical hain! Dono C ke varlena structure use karte hain. TEXT use karein bina kisi dar ke!
💰
Money Math: NUMERIC vs FLOAT
Financial calculation mein kabhi FLOAT ya DOUBLE PRECISION use na karein (floating-point binary rounding errors: 0.1 + 0.2 = 0.30000000000000004). Currency ke liye hamesha NUMERIC(12, 2) use karein (MySQL ke DECIMAL jaisa).
🆔
PK Evolution: SERIAL to UUIDv7
SERIAL ek purana hack hai. Modern PostgreSQL (PG 10+) mein SQL Standard GENERATED ALWAYS AS IDENTITY use hota hai. Distributed apps ke liye UUIDv7 time-ordered hota hai, jo B-tree index ko superfast rakhta hai.

📜 The Great Text Comparison: TEXT vs VARCHAR(n) vs CHAR(n)

Data Type Storage Engine Mechanics Performance Difference When to Use in Real Projects
TEXT Variable length, compressed automatically via TOAST if > 2KB. ⚡ Fast (Zero length check overhead) Default choice for 95% of text columns (names, descriptions, blogs).
VARCHAR(n) Exact same varlena storage as TEXT + length check constraint. ⚡ Same speed (nano-second check) Use only when business strictly demands hard limits (e.g. VARCHAR(10) phone).
CHAR(n) Fixed length with blank padding (spaces fill up unused length). ❌ Slower & wastes space Rarely used. Only for fixed hashes (e.g. SHA-256 hash CHAR(64)).

🔑 Primary Key Showdown: BIGINT vs UUIDv4 vs UUIDv7

Why UUIDv4 Destroys B-Tree Indexes, but UUIDv7 Fixes It

❌ UUIDv4 (Pure Random Entropy)

• Completely random 128-bit hex string.
• Har naya insert B-tree index ke random page par land karta hai.
• Problem: Constant B-tree page splits, random disk writes, and high cache evictions!

✅ UUIDv7 (Time-Ordered + Randomness)

• First 48 bits = Millisecond Unix Timestamp.
• Last 74 bits = Cryptographic Random Entropy.
• Result: Sequential B-Tree appending (same speed as BIGINT!) + Global uniqueness across microservices!

SQL • Modern Table Definition with Best-Practice Primitives 
-- 1. Modern BIGINT Identity (Recommended for internal/admin databases)
CREATE TABLE customers (
    -- Modern SQL standard instead of legacy SERIAL
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    
    -- TEXT is optimal; no arbitrary 255 character limit
    full_name TEXT NOT NULL,
    email TEXT NOT NULL UNIQUE,
    
    -- Fixed-point exact precision for financial billing
    wallet_balance NUMERIC(12, 2) NOT NULL DEFAULT 0.00,
    
    -- Boolean flag
    is_verified BOOLEAN NOT NULL DEFAULT FALSE,
    
    -- Timezone-aware timestamp (Never use plain TIMESTAMP!)
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 2. Distributed SaaS Table using UUIDv7 Primary Keys
-- (In PostgreSQL 17+, gen_random_uuidv7() is native. For PG 14-16, use standard function below:)
CREATE OR REPLACE FUNCTION generate_uuidv7() RETURNS uuid AS $$
DECLARE
    unix_time_ms bytea;
    random_bytes bytea;
BEGIN
    unix_time_ms := substring(int8send(floor(extract(epoch from clock_timestamp()) * 1000)::bigint) from 3 for 6);
    random_bytes := gen_random_bytes(10);
    
    -- Set version 7 and RFC 4122 variant bits
    RETURN encode(
        unix_time_ms || 
        set_byte(substring(random_bytes from 1 for 2), 0, (get_byte(substring(random_bytes from 1 for 2), 0) & 15) | 112) || 
        set_byte(substring(random_bytes from 3 for 8), 0, (get_byte(substring(random_bytes from 3 for 8), 0) & 63) | 128), 
        'hex'
    )::uuid;
END;
$$ LANGUAGE plpgsql VOLATILE;

-- Create orders table with fast UUIDv7
CREATE TABLE orders (
    id UUID PRIMARY KEY DEFAULT generate_uuidv7(),
    customer_id BIGINT REFERENCES customers(id),
    total_amount NUMERIC(10, 2) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
⏰ Time Architecture • Part 2 • Date, Time & TIMESTAMPTZ Traps

Date, Time & Timezones: Avoiding the #1 Production Date Bug

Web applications ka sabse common bug: TIMESTAMP vs TIMESTAMPTZ. Jaaniye PostgreSQL internally time kaise store karta hai, session conversions kaise kaam karte hain, aur INTERVAL arithmetic se clean subscriptions kaise calculate hoti hain.

🐬 MySQL Developer Mental Bridge: DATETIME vs TIMESTAMPTZ (Year 2038 Danger!)

• MySQL DATETIME: MySQL mein DATETIME sirf ek dumb string jaisa hota hai (e.g. 2026-09-09 14:00:00). Ise nahi pata ki yeh UTC hai ya IST. Timezone offset kabhi convert nahi hota.
• MySQL TIMESTAMP (Year 2038 Trap): MySQL ka TIMESTAMP timezone handle karta hai, lekin wo 32-bit integer hai jo 19 January 2038 ko crash ho jayega (Unix 2038 bug)!
• PostgreSQL TIMESTAMPTZ: PostgreSQL ka TIMESTAMPTZ 64-bit microsecond integer hai jo 294,276 AD tak safe hai. Yeh input ko hamesha disk par UTC mein convert karke store karta hai aur client ke session ke hisab se dynamically format karta hai!

🚨
The #1 Date Mistake: Using TIMESTAMP Instead of TIMESTAMPTZ

TIMESTAMP (without timezone) ek deewar par lagi ghadi jaisa hota hai: 2026-09-09 14:00:00. Ise nahi pata ki yeh Delhi ka time hai ya New York ka! Agar Delhi ka user 2 PM par order karta hai, toh California ke admin ko bhi 2 PM hi dikhega (jo ki 9.5 ghante aage hai!).
The Golden Rule: Web applications ke sabhi timestamp columns (created_at, updated_at, paid_at) ke liye hamesha TIMESTAMPTZ use karein!

🧠 How TIMESTAMPTZ Works Internally (The Hidden Secret)

Bohot se developers sochte hain ki TIMESTAMPTZ timezone ka text (e.g. "Asia/Kolkata") disk par store karta hai. Nahi!

🌐
1. Input Conversion to UTC
Jab aap koi time insert karte hain (e.g. 2026-09-09 14:30:00+05:30), PostgreSQL use turant convert karke pure UTC (8-byte integer offset) mein disk par likhta hai.
🔄
2. Output Conversion on the Fly
Jab client SELECT karta hai, PostgreSQL client ke active session timezone (SET timezone = '...') ke hisab se UTC time ko automatically client ke local time mein format karke return karta hai!
🛡️
3. Daylight Saving Proof
US/Europe mein clock 1 ghanta aage/peeche hoti hai (Daylight Saving Time). Kyunki PostgreSQL disk par hamesha UTC store karta hai, daylight saving transition par kabhi data corrupt nahi hota!

📦 Collections & Enums • Part 3 • Native Arrays & Custom Types

PostgreSQL Native Arrays & ENUMs: When to Avoid Pivot Tables

Beginner developers har chhoti cheez ke liye 3 tables aur complex JOIN pivot tables banate hain. Sikhiye kab PostgreSQL ke native Arrays 10x faster hote hain aur custom ENUM types kaise data integrity maintain karte hain.

🐬 MySQL Developer Mental Bridge: No Native Arrays in MySQL vs Postgres TEXT[]

• MySQL (No Arrays): MySQL mein koi native Array data type nahi hota! Developers ya toh comma-separated string banate hain (aur slow FIND_IN_SET() use karte hain) ya fir 3 alag tables (posts, tags, post_tags pivot) banate hain.
• PostgreSQL Native Arrays: PostgreSQL mein TEXT[] ya INT[] first-class citizen hain! Inhe GIN indexes se sub-millisecond search kiya ja sakta hai.
• ENUM Architecture: MySQL mein ENUM table column ke definition se locked hota hai (status ENUM('active','inactive')). Change karne ke liye pura table rewrite (ALTER TABLE MODIFY) hota tha. PostgreSQL mein CREATE TYPE ek independent, reusable database object hota hai jise 100 tables mein reuse kiya ja sakta hai!

🏷️
When to Use Arrays (TEXT[])
Agar data lightweight hai (e.g. blog tags, user roles ['admin', 'finance'], phone numbers) aur unka apna koi extra metadata nahi hai, toh Array column use karein. Zero JOINs, single read!
🔗
When to Use Traditional Pivot Tables
Agar relation entity ke upar apna alag data hai (e.g. assigned_at, granted_by_user_id) ya tag ka apna slug/SEO description hai, toh standard relational many-to-many pivot table banayein.
🛡️
Type-Safe 4-Byte ENUMs
Plain string VARCHAR(20) store karne ke bajaye custom CREATE TYPE ... AS ENUM banayein. Disk par sirf 4 bytes leta hai aur typos (e.g. 'pedning') ko engine level par reject karta hai.

⚡ Core Array Operators: @>, &&, and ANY

Operator / Function Meaning SQL Example Result
@> (Contains) Does left array contain all elements of right array? ARRAY['php', 'postgres', 'vue'] @> ARRAY['postgres'] TRUE
&& (Overlaps) Do both arrays share at least one common element? ARRAY['apple', 'banana'] && ARRAY['banana', 'cherry'] TRUE
= ANY() Does scalar value match any element in array? 'admin' = ANY(roles) TRUE / FALSE
UNNEST() Expands array into individual relational rows. SELECT UNNEST(tags) FROM articles; 1 row per tag
SQL • Practical Array Operations & Custom ENUMs 
-- 1. Create a custom type-safe ENUM for Order Statuses
CREATE TYPE order_status AS ENUM (
    'draft',
    'pending_payment',
    'processing',
    'shipped',
    'delivered',
    'cancelled'
);

-- 2. Create articles table using both ENUM and native TEXT[] Array
CREATE TABLE articles (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title TEXT NOT NULL,
    status order_status NOT NULL DEFAULT 'draft',
    tags TEXT[] NOT NULL DEFAULT '{}',
    published_at TIMESTAMPTZ
);

-- 3. Insert sample data with array literals
INSERT INTO articles (title, status, tags) VALUES 
('Mastering PostgreSQL Internals', 'processing', ARRAY['database', 'postgres', 'backend']),
('Building AI Agents with Laravel', 'shipped', ARRAY['laravel', 'ai', 'php']);

-- 4. Query: Find all articles that have 'postgres' tag (Indexed via GIN!)
SELECT id, title, tags 
FROM articles 
WHERE tags @> ARRAY['postgres'];

-- 5. Query: Find articles that have EITHER 'laravel' OR 'database'
SELECT id, title, tags 
FROM articles 
WHERE tags && ARRAY['laravel', 'database'];

-- 6. Add element to array dynamically in an UPDATE
UPDATE articles 
SET tags = array_append(tags, 'intermediate')
WHERE id = 1;

-- 7. Reporting: Expand arrays into relational rows with UNNEST
SELECT 
    UNNEST(tags) AS tag_name, 
    COUNT(*) AS article_count
FROM articles
GROUP BY tag_name
ORDER BY article_count DESC;

-- 8. Senior Tip: Safely adding new value to an active ENUM in production
ALTER TYPE order_status ADD VALUE 'refunded' AFTER 'cancelled';
⚡ Semi-Structured Data • Part 4 • JSON vs JSONB Binary Mastery

JSON vs JSONB: Why PostgreSQL Beats Dedicated Document Stores

PostgreSQL ke paas do JSON types hain: json aur jsonb. Dono ke beech ka antar samjhiye, core operators (->, ->>, @>) ko master karein, aur partial JSON updates seekhein.

🐬 MySQL Developer Mental Bridge: MySQL JSON vs PostgreSQL JSONB Indexing

• MySQL JSON Limitations: MySQL 8.0 mein JSON column ke andar kisi key ko index karne ke liye aapko Generated Virtual Column banana padta hai (e.g. ALTER TABLE t ADD COLUMN brand VARCHAR(50) AS (data->>'$.brand'), ADD INDEX(brand)). Har nayi JSON key ke liye alag schema alter karna padta hai!
• PostgreSQL JSONB Superpower: PostgreSQL mein aap pure JSON document par ek hi GIN index (USING GIN (attributes jsonb_path_ops)) laga sakte hain. Iske baad aap chahe 1,000 alag dynamic keys par @> search karein, sabhi queries bina naye columns banaye instant sub-millisecond index scan use karti hain!
• Operators: MySQL ka JSON_EXTRACT(data, '$.name') ya data->'$.name' PostgreSQL mein data->'name' aur data->>'name' (clean text) ban jata hai.

💡
Simple Analogy: Plain JSON vs Binary JSONB

• Plain JSON: Ek plain text document jaisa hai. Yeh aapke raw text ko exact whitespace ke sath store karta hai. Write fast hota hai, lekin har search par ise text parse karna padta hai.
• JSONB (Binary JSON): Ek parsed, structured binary tree jaisa hai. Yeh extra spaces hata deta hai, duplicate keys delete kar deta hai, aur keys ko binary format mein index karta hai.
Rule of Thumb: 99% production projects mein hamesha JSONB use karein!

🔍 Master the Core JSONB Operators

Operator Return Type Description Example (data = '{"name": "Pankaj", "age": 28}') Output
-> JSONB Extracts element as JSON object (keeps quotes). data -> 'name' "Pankaj" (jsonb string)
->> TEXT Extracts element as clean SQL TEXT string. data ->> 'name' Pankaj (raw text)
@> BOOLEAN Does left JSONB contain the right JSONB structure? data @> '{"age": 28}' TRUE (GIN Indexable!)
? BOOLEAN Does the top-level string key exist in JSONB? data ? 'name' TRUE
- JSONB Deletes a key or index from the JSONB object. data - 'age' {"name": "Pankaj"}
SQL • Real-World E-Commerce Products Table with JSONB 
-- 1. Create table with dynamic product specifications
CREATE TABLE products (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title TEXT NOT NULL,
    price NUMERIC(10, 2) NOT NULL,
    -- Flexible schema for dynamic product attributes (color, ram, storage, warranty)
    attributes JSONB NOT NULL DEFAULT '{}'::jsonb
);

-- 2. Insert diverse semi-structured records
INSERT INTO products (title, price, attributes) VALUES 
(
    'MacBook Pro 16', 
    2499.00, 
    '{"category": "laptop", "ram_gb": 32, "storage_gb": 1000, "brand": "Apple", "colors": ["silver", "space_gray"]}'
),
(
    'Wireless Mechanical Keyboard', 
    149.00, 
    '{"category": "accessory", "switch": "Cherry MX Red", "wireless": true, "bluetooth": true}'
);

-- 3. Query 1: Extract text value for WHERE condition
SELECT title, price, attributes->>'brand' AS brand
FROM products
WHERE attributes->>'category' = 'laptop';

-- 4. Query 2: Numeric filtering (Cast text to integer)
SELECT title, price, (attributes->>'ram_gb')::INT AS ram
FROM products
WHERE (attributes->>'ram_gb')::INT >= 16;

-- 5. Query 3: Containment check using @> (Lightning-fast with GIN index!)
SELECT title, price 
FROM products
WHERE attributes @> '{"wireless": true}';

-- 6. Query 4: Updating a single nested key without overwriting the entire JSON document
-- jsonb_set(target_column, '{path,to,key}', 'new_value'::jsonb)
UPDATE products
SET attributes = jsonb_set(attributes, '{ram_gb}', '64'::jsonb)
WHERE id = 1;

-- 7. Query 5: Create a GIN index on attributes for instant JSON search
CREATE INDEX idx_products_attributes ON products USING GIN (attributes jsonb_path_ops);
📅 Temporal Ranges • Part 5 • Range Types & Anti-Double-Booking

Range Types & The Impossible Bug: Eliminating Double-Booking Forever

Hotel booking, doctor appointments, aur meeting rooms mein Double Booking race conditions application code se rokna impossible hota hai. Jaaniye kaise PostgreSQL ke Range Types aur EXCLUDE constraints is problem ko hamesha ke liye solve kar dete hain.

🐬 MySQL Developer Mental Bridge: MySQL Table Locks vs PostgreSQL EXCLUDE

• How MySQL Handles Overlap: MySQL ke paas koi Range data types ya Exclusion constraints nahi hote! Double-booking rokne ke liye MySQL developers ko ya toh pura table lock (LOCK TABLES bookings WRITE) karna padta hai, ya pessimistic row-level locking (SELECT ... FOR UPDATE) chalani padti hai, jo concurrent high traffic par heavy deadlocks aur slow performance cause karti hai.
• How PostgreSQL Solves It: PostgreSQL mein TSTZRANGE ek native scalar data type hai, aur EXCLUDE USING gist GiST R-Tree index use karta hai. Database engine kisi bhi do overlapping intervals ko same room par aane hi nahi deta—chahe 10,000 requests concurrent execute ho rahi hon! Zero application code, zero race condition!

⚡
The Real-World Race Condition Nightmare

Sochiye do users ek hi second mein Room 101 book karne ki koshish karte hain:
• User A: 10:00 AM to 11:00 AM
• User B: 10:30 AM to 11:30 AM
Agar aap application code mein if (!Booking::exists(...)) likhte hain, toh dono requests simultaneous execution ki wajah se if pass kar lengi, aur dono bookings database mein insert ho jayengi!

📐 Understanding Range Types & Bracket Notation

PostgreSQL do alag columns (start_date aur end_date) ke bajaye ek single Range Type provide karta hai:

📅
daterange & tstzrange
Date ranges (hotels) ya Timestamp ranges (doctor appointments) ko single unit ki tarah store karta hai. Example: '[2026-05-01, 2026-05-05)'::daterange.
🔲
Bracket vs Parenthesis Notation
[ (Square bracket) means Inclusive (is point ko include karo).
) (Parenthesis) means Exclusive (is point ke pehle stop ho jao - perfect for check-out day!).
⚔️
The Overlap Operator (&&)
Do ranges aapas mein takra rahi hain ya nahi, yeh check karne ke liye simple range1 && range2 operator use hota hai. Zero complex date math required!

🛡️ The Magic Constraint: EXCLUDE USING gist

Yeh PostgreSQL ka sabse powerful constraint hai. Yeh database engine level par enforce karta hai ki: "Kisi bhi same room_id ke liye booking range kabhi aapas mein overlap (&&) nahi ho sakti!"

SQL • Complete Double-Booking Prevention Schema 
-- 1. Enable btree_gist extension (Required to combine scalar = with range &&)
CREATE EXTENSION IF NOT EXISTS btree_gist;

-- 2. Create conference room reservations table
CREATE TABLE room_bookings (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_id INT NOT NULL,
    booked_by TEXT NOT NULL,
    -- tstzrange stores start and end timestamp as a single continuous span
    booking_time TSTZRANGE NOT NULL,
    
    -- THE MAGIC EXCLUSION CONSTRAINT:
    -- If room_id is EQUAL (=), booking_time MUST NOT OVERLAP (&&)
    CONSTRAINT no_overlapping_room_bookings 
        EXCLUDE USING gist (
            room_id WITH =, 
            booking_time WITH &&
        )
);

-- 3. TEST 1: First booking for Room 101 (10:00 to 11:00) -> SUCCESS!
INSERT INTO room_bookings (room_id, booked_by, booking_time) VALUES (
    101, 
    'Rahul Sharma', 
    tstzrange('2026-09-15 10:00:00+05:30', '2026-09-15 11:00:00+05:30')
);

-- 4. TEST 2: Overlapping booking for Room 101 (10:30 to 11:30) -> BLOCKED!
-- Database immediately throws:
-- ERROR: conflicting key value violates exclusion constraint "no_overlapping_room_bookings"
INSERT INTO room_bookings (room_id, booked_by, booking_time) VALUES (
    101, 
    'Priya Patel', 
    tstzrange('2026-09-15 10:30:00+05:30', '2026-09-15 11:30:00+05:30')
);

-- 5. TEST 3: Booking Room 102 at the exact same time -> SUCCESS!
-- Because room_id is different, no conflict occurs!
INSERT INTO room_bookings (room_id, booked_by, booking_time) VALUES (
    102, 
    'Priya Patel', 
    tstzrange('2026-09-15 10:30:00+05:30', '2026-09-15 11:30:00+05:30')
);
🛡️ Schema Integrity • Part 6 • Advanced Table Constraints

Enterprise Schema Constraints: Defense-in-Depth Beyond Application Code

Application-level validation (Laravel FormRequests / Zod) zaroori hai, lekin data integrity ki final guarantee database engine deta hai. Sikhiye multi-column CHECK constraints, SaaS-saving Partial Unique Indexes, aur safe Foreign Key cascades.

🐬 MySQL Developer Mental Bridge: Ignored CHECK Constraints & Partial Indexes

• MySQL CHECK Constraint History: MySQL 8.0.16 se pehle, MySQL CHECK syntax ko parse toh karta tha lekin silently IGNORE kar deta tha! Is wajah se kayi MySQL developers ko database-level validation par vishwas nahi rehta tha. PostgreSQL mein CHECK constraints Day 1 se rock-solid, super-strict aur fast hain!
• No Partial Indexes in MySQL: MySQL mein partial indexes (filtered indexes) exist nahi karte! Agar aapko UNIQUE(user_id) WHERE status = 'active' chahiye, toh MySQL mein gande hacks karne padte hain (jaise generated virtual column with NULL). PostgreSQL mein native WHERE clause index banta hai jo sirf matching rows index karta hai!

🚦
Why App Validation is Not Enough
Direct SQL scripts, background queues, automated seeder scripts, ya background microservices application validation ko bypass kar sakte hain. Database constraints ensure karte hain ki corrupt data kabhi table mein ghus hi na sake.
🎯
Partial Unique Indexes
Pura table unique karne ke bajaye sirf filtered rows par uniqueness lagayein. Example: User ke 10 purane cancelled subscriptions ho sakte hain, lekin status = 'active' wala sirf 1 hi ho sakta hai!
💣
The CASCADE Deletion Danger
ON DELETE CASCADE dangerous hota hai. Agar kisi ne galti se 1 organization delete ki, toh uske 200,000 invoices aur payments bina kisi warning ke vanish ho jaate hain! Financial tables par hamesha RESTRICT use karein.

🛡️ Real-World Multi-Column CHECK Constraints

PostgreSQL mein CHECK constraints columns ke beech ke mathematical relations validate kar sakte hain:

SQL • Production Invoices Table with Strict Constraints 
-- Production Invoicing Table with Mathematical & Text Integrity
CREATE TABLE invoices (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    invoice_number TEXT NOT NULL UNIQUE,
    
    subtotal NUMERIC(10, 2) NOT NULL,
    discount NUMERIC(10, 2) NOT NULL DEFAULT 0.00,
    tax_amount NUMERIC(10, 2) NOT NULL DEFAULT 0.00,
    total_amount NUMERIC(10, 2) NOT NULL,
    
    status TEXT NOT NULL DEFAULT 'draft',
    due_date DATE NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    -- 1. Constraint: Subtotal and amounts must be non-negative
    CONSTRAINT positive_amounts CHECK (
        subtotal >= 0 AND 
        discount >= 0 AND 
        tax_amount >= 0
    ),

    -- 2. Constraint: Discount cannot exceed the subtotal!
    CONSTRAINT discount_within_limit CHECK (
        discount <= subtotal
    ),

    -- 3. Constraint: Total must equal (subtotal - discount + tax)
    CONSTRAINT accurate_total_calculation CHECK (
        total_amount = (subtotal - discount + tax_amount)
    ),

    -- 4. Constraint: Clean non-empty string check
    CONSTRAINT non_empty_invoice_number CHECK (
        length(trim(invoice_number)) >= 3
    )
);

⚡ The SaaS Partial Unique Index Pattern

Agar aap standard UNIQUE(user_id) lagayenge, toh user dubara kabhi subscribe nahi kar payega. Partial index se sirf active status filter hota hai:

SQL • Partial Unique Index for SaaS Subscriptions 
CREATE TABLE subscriptions (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL,
    plan_code TEXT NOT NULL,
    status TEXT NOT NULL, -- 'active', 'cancelled', 'past_due', 'expired'
    current_period_end TIMESTAMPTZ NOT NULL
);

-- PARTIAL UNIQUE INDEX:
-- Enforces that a user can have at most ONE 'active' subscription!
-- Cancelled, expired, or past_due rows can exist multiple times for the same user.
CREATE UNIQUE INDEX unique_active_user_subscription 
ON subscriptions (user_id) 
WHERE status = 'active';

-- TEST:
-- Insert 1: User 42 has cancelled sub -> SUCCESS
INSERT INTO subscriptions (user_id, plan_code, status, current_period_end) 
VALUES (42, 'pro_monthly', 'cancelled', NOW() - INTERVAL '1 month');

-- Insert 2: User 42 has another expired sub -> SUCCESS
INSERT INTO subscriptions (user_id, plan_code, status, current_period_end) 
VALUES (42, 'starter', 'expired', NOW() - INTERVAL '15 days');

-- Insert 3: User 42 subscribes to active pro -> SUCCESS
INSERT INTO subscriptions (user_id, plan_code, status, current_period_end) 
VALUES (42, 'pro_yearly', 'active', NOW() + INTERVAL '1 year');

-- Insert 4: Attempting a second active sub for User 42 -> BLOCKED!
-- ERROR: duplicate key value violates unique constraint "unique_active_user_subscription"
INSERT INTO subscriptions (user_id, plan_code, status, current_period_end) 
VALUES (42, 'enterprise', 'active', NOW() + INTERVAL '1 year');

4 YOE Schema Design Pitfalls & Master Data Types Cheatsheet

Aise 4 fatal mistakes jo 4 YOE engineers ke production systems ko crash kar dete hain, aur Module 02 ka complete quick-reference cheatsheet.

1. The JSONB "Dumping Ground" Trap
Kayi developers schema migration se bachne ke liye table mein ek bada data JSONB column banate hain aur relational model bhool jaate hain. Disaster: Zero Foreign Keys, relational JOINs slow ho jaate hain, aur partial index maintenance mushkil ho jati hai. Sirf truly dynamic attributes ke liye JSONB use karein!
2. SERIAL Integer Overflow Outage
High-write tables (jaise audit_logs, stripe_events, user_clicks) mein SERIAL (32-bit INT) lagane par jaise hi rows 2.14 Billion cross karti hain, application par sabhi INSERTs fail ho jaate hain! High-write tables par hamesha BIGINT use karein.
3. Unindexed Foreign Keys in PostgreSQL
MySQL InnoDB foreign key par automatically index bana deta hai, lekin PostgreSQL Foreign Keys par index nahi banata! Agar aapne child_table.customer_id par manual index nahi banaya, toh parent record delete karte waqt PostgreSQL pura child table sequentially scan karega!

📋 Master Data Types Quick-Reference Cheatsheet

Category Recommended Data Type When to Use in Real Projects Common Mistake to Avoid
Primary Key BIGINT IDENTITY or UUIDv7 BIGINT for internal single-DB apps; UUIDv7 for microservices/distributed SaaS. Avoid legacy SERIAL or random UUIDv4.
Text / Strings TEXT Names, bios, descriptions, emails, slugs. Avoid arbitrary VARCHAR(255) limit without business need.
Money & Math NUMERIC(12, 2) Prices, ledger balances, transaction fee amounts. Never use FLOAT or DOUBLE PRECISION for billing!
Timestamps TIMESTAMPTZ Event logs, created_at, updated_at, scheduled tasks. Never use plain TIMESTAMP in web applications.
Collections TEXT[] or INT[] Lightweight tags, roles, permissions without extra metadata. Don't use if elements require their own foreign keys/metadata.
Semi-Structured JSONB (with GIN index) Dynamic e-commerce specs, third-party webhook payloads. Avoid plain JSON; always index with jsonb_path_ops.
Scheduling TSTZRANGE + EXCLUDE Hotel rooms, doctor shifts, meeting room bookings. Don't rely on application code to prevent double-booking overlaps!
