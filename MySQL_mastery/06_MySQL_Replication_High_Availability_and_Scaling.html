Interactive: Order Payment Transaction — Safe Execution Pipeline

"Buy Now" click se lekar payment confirm hone tak ek safe transaction ka step-by-step flow:

Transaction Patterns — Kab Kya Use Karein?
Pattern Code Best For Drawback
DB::transaction(closure) DB::transaction(fn() => ...) Simple multi-operation transactions No partial commit possible
Manual begin/commit/rollback beginTransaction(), commit() Complex flows needing partial control Must handle rollback in catch
With retry attempts DB::transaction(fn, attempts: 3) High-concurrency; deadlock-prone tables Idempotent operations only
Nested (Savepoints) Nested DB::transaction() Complex services with sub-transactions Laravel manages savepoints automatically 

// GOLDEN RULE: Transaction ke andar sirf DB operations karo!
// WRONG:
DB::transaction(function () use ($order) {
    $order->update(['status' => 'confirmed']);
    Mail::to($order->user)->send(new OrderConfirmed($order)); // WRONG! Email in transaction!
    // Agar email fail ho = order rollback! Email service DB se related nahi!
});

// CORRECT: DB operations transaction mein, side effects baad mein
DB::transaction(function () use ($order) {
    $order->update(['status' => 'confirmed']);
    // Sirf DB operations yahan
});
// Transaction ke baad email bhejo:
Mail::to($order->user)->send(new OrderConfirmed($order));
// Ya better: Queue mein daalo
dispatch(new SendOrderConfirmationJob($order));
Race Condition — lockForUpdate() Se Fix Karo

Last item ki rush purchase scenario — do users ek sath try karte hain:

Without LockWith lockForUpdate()
User A reads stock = 1 ✅ User A: SELECT ... FOR UPDATE — gets lock ✅
User B reads stock = 1 ✅ (before A updates) User B: SELECT ... FOR UPDATE — WAITS ⏳
User A decrements stock to 0 User A: stock = 1, decrements to 0, commits
User B ALSO decrements stock to -1 ❌ User B: lock released, reads stock = 0 → Out of Stock ✅
Result: Oversold! Stock = -1 Result: Correct! Only 1 order placed 
// Correct implementation with lockForUpdate:
public function purchaseProduct(int $productId, int $userId, int $qty): Order
{
    return DB::transaction(function () use ($productId, $userId, $qty) {
        // Exclusive lock — sirf ek request ek waqt mein yahan rahegi
        $product = Product::lockForUpdate()->findOrFail($productId);

        if ($product->stock < $qty) {
            throw new InsufficientStockException(
                "Only {$product->stock} items available"
            );
        }

        // Safe decrement:
        $product->decrement('stock', $qty);

        // Create order:
        $order = Order::create([
            'user_id'    => $userId,
            'product_id' => $productId,
            'qty'        => $qty,
            'total'      => $product->price * $qty,
            'status'     => 'confirmed',
        ]);

        return $order;
        // Lock releases on transaction commit
    });
}
Deadlock Prevention — 4 Golden Rules
// RULE 1: Consistent lock order (MOST IMPORTANT!)
// ALWAYS lock in same order across all transactions:
// users -> orders -> products (never reverse!)

// WRONG (can deadlock if two transactions run simultaneously):
// Tx A: lock user(1), then order(5)
// Tx B: lock order(5), then user(1) -- DEADLOCK!

// CORRECT: Both Tx lock in same order:
DB::transaction(function () {
    $user = User::lockForUpdate()->find(1);   // ALWAYS FIRST
    $order = Order::lockForUpdate()->find(5); // ALWAYS SECOND
});

// RULE 2: Minimal transaction scope
DB::transaction(function () use ($data) {
    // Only DB operations -- no API calls, file I/O, sleep()
    Order::create($data);
    Product::where('id', $data['product_id'])->decrement('stock');
}); // Transaction ends immediately after DB work

// RULE 3: Use built-in retry
DB::transaction(function () {
    // Your operations
}, attempts: 3); // Deadlock par 3 baar try karega

// RULE 4: Catch & handle deadlock gracefully
use IlluminateDatabaseQueryException;

try {
    DB::transaction(function () { ... });
} catch (QueryException $e) {
    if ($e->errorInfo[1] === 1213) { // MySQL deadlock error code
        Log::warning('Deadlock detected, retrying...');
        // Queue mein daalo ya user ko retry suggest karo
        throw new RetryableException('Please try again in a moment');
    }
    throw $e;
}
Foreign Key Cascades — E-Commerce Strategy Guide
Cascade Type Laravel Method Behavior When to Use
RESTRICT ->restrictOnDelete() Parent delete blocked if children exist Users with orders — protect history
CASCADE ->cascadeOnDelete() Children auto-deleted with parent Cart items when cart deleted
SET NULL ->nullOnDelete() FK set to NULL when parent deleted Product category deleted — keep product
NO ACTION Default (same as RESTRICT) Error on parent delete Strict data integrity needed 
// E-commerce FK Strategy Example:
// users -> RESTRICT orders (history must be preserved)
// orders -> CASCADE order_items (meaningless without order)
// orders -> RESTRICT payments (financial data never auto-delete)
// products -> SET NULL order_items.product_id (history preserved, product can be deleted)
// categories -> SET NULL products.category_id (uncategorize, dont delete products)
// carts -> CASCADE cart_items (cart deleted = items deleted too)

Schema::create('order_items', function (Blueprint $table) {
    $table->id();
    $table->foreignId('order_id')
          ->constrained()
          ->cascadeOnDelete();       // Order deleted = items deleted

    $table->foreignId('product_id')
          ->nullable()               // Must be nullable for SET NULL!
          ->constrained()
          ->nullOnDelete();          // Product deleted = null here, not deleted

    $table->unsignedInteger('qty');
    $table->decimal('unit_price', 10, 2); // Snapshot of price at purchase time
    $table->timestamps();
});
