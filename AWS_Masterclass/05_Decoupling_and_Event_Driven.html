Decoupling & Event-Driven Architecture

Node.js single-threaded hota hai. Agar user sign-up kare aur aap wahin par PDF generate karke email bhejne lago, toh apka API response 5 seconds lega aur server hang ho jayega. Backend ko "Decouple" karna seekhein.

🧱 Architecture • Part 1

Tightly Coupled Monoliths

"Tight Coupling" ka matlab hai jab ek system doosre ka wait karta hai kaam poora hone ke liye.

❌ Synchronous Flow (Slow)

User -> POST /signup -> DB Save (50ms) -> PDF Generate (2000ms) -> Send Email (1000ms) -> Return Response.
Result: User ko loading spinner 3 seconds tak dikhta hai. Agar Email server down hai, toh pura API fail ho jayega!

✅ Asynchronous Flow (Fast)

User -> POST /signup -> DB Save (50ms) -> Send message to Queue (10ms) -> Return Response!
Result: User ko 60ms me success mil gaya. Background me ek alag "Worker" aaram se PDF banayega aur email bhejega. Isko Decoupling bolte hain.

📥 Queues • Part 2

Amazon SQS (Simple Queue Service)

SQS ek post office box ki tarah hai. Aap messages (JSON) yahan daal dete ho, aur workers apni speed se unhe uthate hain.

  • Producer (Web Server): API request aate hi JSON message banata hai { "userId": 123, "action": "send_welcome_email" } aur SQS me bhej deta hai.
  • Queue (SQS): Message ko safe rakhta hai. SQS guarantee deta hai ki message ghum nahi hoga.
  • Consumer (Worker Server/Lambda): Lagatar SQS ko check karta rehta hai (Polling). Message uthata hai, email bhejta hai, aur phir queue se delete kar deta hai taaki koi aur worker use dubara na bheje.

⚠️ Standard vs FIFO

Standard Queue: Bahut fast hoti hai, par messages ka order guarantee nahi hota. Kabhi kabhi ek message 2 baar bhi deliver ho sakta hai (At-least-once delivery).
FIFO Queue (First-In-First-Out): Order maintain rakhti hai aur exactly ek hi baar message bhejti hai. Banking transactions ke liye FIFO use karein.

📢 Pub/Sub • Part 3

Amazon SNS (Simple Notification Service)

SQS "One-to-One" hota hai (Ek message, ek worker ko milta hai). Par kya hoga agar ek "User Signup" event par aapko 3 alag-alag cheezein karni hon? (Email bhejna, Analytics update karna, Push notification bhejna).

The Fan-out Architecture (SNS + SQS)

  1. Node.js Server ek Topic banata hai (e.g., `UserSignupTopic`) aur usme ek notification "Publish" (Pub) karta hai.
  2. Us Topic ko 3 alag-alag SQS Queues ne Subscribe (Sub) kiya hua hai (Email Queue, Analytics Queue, Push Queue).
  3. SNS turant us ek message ki 3 copies banata hai aur teeno queues me daal deta hai (Fan-out).
  4. Teeno background workers apna apna kaam parallel me shuru kar dete hain!

Note: AWS EventBridge bhi similar pattern follow karta hai, par wo SaaS apps (like Zendesk, Datadog) se directly connect karne me zyada powerful hai. Modern serverless me EventBridge kaafi popular ho raha hai.

💻 Code • Part 4

Sending Messages to SQS via Node.js

SDK v3 use karke Express app se message Queue me kaise push karein.

TypeScript • Sending to SQS 
import { SQSClient, SendMessageCommand } from "@aws-sdk/client-sqs";

const sqsClient = new SQSClient({ region: "ap-south-1" });
const QUEUE_URL = "https://sqs.ap-south-1.amazonaws.com/123456789/WelcomeEmailQueue";

app.post('/api/signup', async (req, res) => {
    const { email, name } = req.body;
    
    // 1. Fast DB Save (e.g., RDS)
    const user = await db.users.create({ email, name });

    // 2. Create the message payload
    const jobData = {
        userId: user.id,
        email: user.email,
        type: "WELCOME_EMAIL"
    };

    // 3. Push to SQS
    await sqsClient.send(new SendMessageCommand({
        QueueUrl: QUEUE_URL,
        MessageBody: JSON.stringify(jobData),
        DelaySeconds: 0 // Optional: Delay processing by X seconds
    }));

    // 4. Return immediately (Fast API!)
    return res.json({ 
        success: true, 
        message: "User created. Check your email shortly." 
    });
});
