🛡️ Fundamentals • Part 1

What is IAM? (The Bouncer of AWS)

Identity and Access Management (IAM) decide karta hai ki "Kaun" (Who) AWS ke andar aa sakta hai aur "Kya" (What) kar sakta hai.

Identity (Who)
Authentication. AWS ko kaise pata chalega ki aap wahi ho jo aap claim kar rahe ho? Iske liye hum Users ya Roles use karte hain.
Access (What)
Authorization. Agar login ho gaye, toh kya S3 se file delete karne ki permission hai? Ye Policies decide karti hain.

🚨 The Root Account Rule

Jab aap AWS pe sign up karte ho, jo email address use hota hai usko "Root Account" bolte hain. Golden Rule: Root account se kabhi daily backend tasks mat karo! Usme MFA lagao aur usko bhool jao. Apne dev kaam ke liye ek naya IAM User banao jise sirf utni hi power ho jitni zaroorat hai.

🎭 Advanced • Part 2

IAM Users vs IAM Roles (The Big Mistake)

Naye backend devs humesha apne .env file mein AWS_ACCESS_KEY_ID aur AWS_SECRET_ACCESS_KEY save kar dete hain. Yeh practice locally theek hai, par production (EC2) par bahut khatarnak hai!

❌ The Junior Developer Way (Users)

Ek IAM User banate hain. Uska long-term Access Key nikalte hain, aur production EC2 server ki .env file mein daal dete hain.

Risk: Agar kisi ne server hack kar liya ya Github par .env commit kar diya, toh hacker ko permanent access mil jayega! Hacker aapke account pe $10,000 ke Bitcoin mining servers chala dega.

✅ The Senior Backend Way (Roles)

Production servers (EC2/ECS) ke andar hum Access Keys nahi daalte! Hum ek IAM Role banate hain aur us role ko EC2 instance ko pehna dete hain ("Attach to EC2").

Benefit: AWS automatically har kuch ghanto me temporary access tokens rotate karta hai. Hacker ko token mila bhi toh thodi der me useless ho jayega. No keys to leak!

Simple rule:
- IAM Users: Humans (aap aur main) ke liye hote hain. Jinke paas password ya long-term keys hoti hain.
- IAM Roles: Machines (EC2, Lambda, Node.js App) ke liye hote hain. Jo temporary credentials assume karti hain.

📜 Permissions • Part 3

IAM Policies (JSON Documents)

Aapne User ya Role toh bana liya, par usko permit kaise karein? AWS me har permission ek JSON document se define hoti hai jisko "Policy" bolte hain.

Har Policy statement ke 4 main hisse hote hain (A.R.E.C): Action, Resource, Effect, Condition.

JSON • IAM Policy Example 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      // Effect: Kya hum Allow kar rahe hain ya Deny?
      "Effect": "Allow",
      
      // Action: AWS ki kaunsi API call allow karni hai?
      "Action": [
        "s3:PutObject",    // Upload file
        "s3:GetObject"     // Download file
      ],
      
      // Resource: Kis specific cheez par? (ARN: Amazon Resource Name)
      "Resource": "arn:aws:s3:::my-nodejs-app-bucket/*"
    }
  ]
}

💡 Principle of Least Privilege

Naye developers tang aakar "Action": "*" (Full Access) de dete hain S3 par. Ye galat hai. Agar aapki app sirf photo upload karti hai, toh policy mein sirf s3:PutObject hona chahiye, s3:DeleteBucket nahi! Isko "Least Privilege" kehte hain.

🚀 Implementation • Part 4

Node.js Integration with IAM

Jab aap AWS SDK v3 use karte hain Node.js mein, toh aap credentials kaise pass karte hain?

TypeScript / Node.js • The Magic of Default Provider 
import { S3Client, ListBucketsCommand } from "@aws-sdk/client-s3";

// Humne yahan KOI credentials pass nahi kiye!
const s3Client = new S3Client({ region: "ap-south-1" });

export const testConnection = async () => {
    try {
        const data = await s3Client.send(new ListBucketsCommand({}));
        console.log("Success! Connected to AWS.");
    } catch (err) {
        console.error("Failed!", err);
    }
};

🤔 Wait, bina keys ke SDK kaam kaise karega?

Yehi AWS SDK ka sabse bada magic hai, jisko "Credential Provider Chain" bolte hain:

  1. Sabse pehle SDK Node.js ke process.env.AWS_ACCESS_KEY_ID mein dhoondhta hai. (Hum dev environment me `dotenv` ya `.bashrc` use karke variables set karte hain).
  2. Agar nahi mila, toh wo aapke laptop ke ~/.aws/credentials file me dhoondhta hai.
  3. Agar app production EC2 par chal rahi hai, toh wahan env vars nahi hote. Toh SDK directly us EC2 instance ki Metadata Service (IAM Role) ko ping karke securely temporary tokens le aata hai!

Isiliye best practice ye hai ki code me new S3Client({ credentials: { ... } }) kabhi hardcode mat karo. SDK ko automatically resolve karne do!
